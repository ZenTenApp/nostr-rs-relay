# Nostr Client Authentication (NIP-42)

Nostr relays can authenticate clients using [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md). Authentication proves that the client currently connected to a relay controls a specific Nostr private key.

This document describes the general NIP-42 flow, with behavior in this repository used as a concrete reference implementation.

## Overview

NIP-42 authentication is a challenge-response protocol over an existing WebSocket connection:

1. The client connects to a relay.
2. The relay sends an authentication challenge.
3. The client creates and signs a special authentication event.
4. The client sends that event back using an `AUTH` command.
5. The relay validates the event and associates the connection with the event's pubkey.

Authentication is connection-scoped. If the WebSocket disconnects, the client must authenticate again on the next connection.

## Relay Challenge

When a relay wants the client to authenticate, it sends an `AUTH` message:

```json
["AUTH", "<challenge>"]
```

The challenge is an opaque string generated by the relay. Clients should not interpret it; they should include it exactly in the authentication event.

In this repository, the challenge is generated per connection as a UUID when NIP-42 auth is enabled.

## Client Authentication Event

To authenticate, the client signs a Nostr event with kind `22242`.

Example:

```json
{
  "id": "<event id>",
  "pubkey": "<client pubkey>",
  "created_at": 1234567890,
  "kind": 22242,
  "tags": [
    ["relay", "wss://relay.example.com/"],
    ["challenge", "<challenge from relay>"]
  ],
  "content": "",
  "sig": "<signature>"
}
```

The event must be signed by the private key corresponding to the event's `pubkey`.

## Client AUTH Command

After creating and signing the authentication event, the client sends it to the relay as an `AUTH` command:

```json
[
  "AUTH",
  {
    "id": "<event id>",
    "pubkey": "<client pubkey>",
    "created_at": 1234567890,
    "kind": 22242,
    "tags": [
      ["relay", "wss://relay.example.com/"],
      ["challenge", "<challenge from relay>"]
    ],
    "content": "",
    "sig": "<signature>"
  }
]
```

## Validation Requirements

A relay should validate the authentication event before accepting it.

Common validation checks include:

1. The relay previously sent a challenge on this connection.
2. The event is a valid Nostr event.
3. The event signature is valid for the event `pubkey`.
4. The event kind is `22242`.
5. The event has a recent `created_at` timestamp.
6. The event has a `challenge` tag matching the relay's challenge.
7. The event has a `relay` tag matching the relay being authenticated to.

This repository's implementation performs these checks and requires the timestamp to be within 10 minutes of the server's current time.

For relay URL validation, this repository compares the host from the event's `relay` tag against the host from the configured relay URL.

## Success and Failure Responses

Relays commonly respond to an authentication attempt using an `OK` message for the authentication event.

Successful authentication:

```json
["OK", "<auth event id>", true, ""]
```

Failed authentication:

```json
["OK", "<auth event id>", false, "restricted: authentication error"]
```

Exact failure messages vary by relay implementation.

## What Authentication Means

After successful authentication, the relay treats the WebSocket connection as authenticated as the pubkey from the authentication event.

For example, if the auth event has:

```json
"pubkey": "abcdef..."
```

then the relay can associate that connection with `abcdef...`.

Authentication does not necessarily mean the client can publish or read everything. It only gives the relay a verified client identity. The relay's authorization rules decide what that identity is allowed to do.

## Common Uses

### Private or Privileged Reads

A relay may require authentication before returning certain events. For example, a relay may only allow a client to read an event if the authenticated pubkey is:

1. the event author, or
2. listed in one of the event's `p` tags.

This pattern is commonly used for direct messages or other private/participant-only event kinds.

This repository supports this style of read control through kind filters with privileged read access.

### Direct Message Filtering

Some relays restrict direct-message-like event kinds so that only the sender or intended recipient can receive them. This usually requires the client to authenticate first, so the relay knows which pubkey is making the request.

### Write Authorization

A relay may also use the authenticated pubkey when deciding whether to accept published events. However, NIP-42 authentication by itself does not require a relay to reject unauthenticated writes. That is a relay policy decision.

A relay may choose to:

- allow unauthenticated writes,
- require authentication for all writes,
- require authentication only for some event kinds,
- compare the authenticated pubkey to the event author,
- pass the authenticated pubkey to an external authorization service.

## Client Checklist

To authenticate with a NIP-42 relay, a client should:

1. Open a WebSocket connection to the relay.
2. Wait for an auth challenge:

   ```json
   ["AUTH", "<challenge>"]
   ```

3. Create a kind `22242` event with:
   - `pubkey` set to the client's pubkey,
   - `created_at` set to the current Unix timestamp,
   - `kind` set to `22242`,
   - `content` usually set to an empty string,
   - a `relay` tag for the relay URL,
   - a `challenge` tag containing the challenge from the relay.

4. Sign the event with the client's private key.
5. Send the signed event as:

   ```json
   ["AUTH", <signed auth event>]
   ```

6. Check for a successful `OK` response.

## Example Auth Event Shape

```json
[
  "AUTH",
  {
    "id": "...",
    "pubkey": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "created_at": 1710000000,

    "tags": [
      ["relay", "wss://relay.example.com/"],

    ],
    "content": "",
    "sig": "..."
  }
]
```

## Common Failure Cases

Authentication can fail if:

- the client sends `AUTH` before receiving a challenge,
- the challenge tag is missing,
- the challenge does not match,
- the relay tag is missing,
- the relay tag points to the wrong relay,
- the event kind is not `22242`,
- the event timestamp is too old or too far in the future,
- the event id or signature is invalid,
- the relay has NIP-42 authentication disabled or unsupported.
